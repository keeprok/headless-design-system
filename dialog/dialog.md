# 끄적임

## 📝 1차 뼈대 (Dialog.Root) 설계 노트 및 끄적임

**Q1. Input은 상태를 외부에 맡겼는데, 왜 Dialog는 내부에서 관리할까?**

- **결론 (상태 소유권의 차이):** Input은 비즈니스 로직(Form)과 직결되므로 상태를 위임(Headless)했지만, Dialog의 Open 상태는 순수 UI 로직이므로 부모를 오염시키지 않기 위해 Root 내부에서 Context로 캡슐화했다. (컴포넌트의 성격에 따른 트레이드오프 타협)

**Q2. `useDialogContext` 안에서 에러(`throw new Error`)를 던지는 이유가 뭘까?**

- **결론 (DX - 개발자 경험 고려):** Root 밖에서 서브 컴포넌트를 사용하는 실수를 런타임에 조기 차단(Fail-Fast)하기 위한 의도적인 방어 로직이다.

**Q3. Context 초기값 타입에 굳이 `null`이 포함되어야 하는 이유는?**

- **결론 (타입 좁히기와 안정성 보장):** `createContext`로 통신망을 뚫는 최초의 순간(Provider가 값을 넣기 직전)에는 값이 비어있을 수밖에 없으므로 논리적으로 `null`이 맞다. 이후 `useDialogContext`에서 `null`을 체크하고 에러를 던져줌으로써(Type Narrowing), 이 훅을 가져다 쓰는 모든 하위 컴포넌트는 "여기엔 절대 null이 없고 무조건 안전한 상태값이 들어있다"고 타입스크립트에게 100% 보장받을 수 있다.

**[추가 끄적임: Trigger의 위치 제약에 대한 고찰]**

- "처음엔 Trigger가 꼭 Provider 안에 있어야 하나 의문이 들었다. 밖에서 열게 하면 편하지 않나?"
- **결론:** 그렇게 하면 전역 상태를 오염시키게 된다. 한 화면에 모달이 여러 개일 때 상태 충돌을 막고, 각 모달이 완벽히 독립적인 생태계(캡슐화)를 가지려면 Trigger와 Content가 반드시 하나의 Root(Provider) 아래로 묶여야만 한다. 이것이 컴포넌트의 '응집도'를 높이는 Compound Component 패턴의 핵심 이유다.

**[추가 끄적임: 중첩 모달(Nested Modals) 처리 원리]**

- "모달 안에서 또 모달을 열면 상태가 충돌하지 않을까 고민했다."
- **결론:** Context API는 가장 가까운 조상 Provider의 값을 구독하므로, 각 모달을 `Dialog.Root`로 각각 감싸주기만 하면 상태는 완벽히 격리된다. 또한, UI가 부모 모달의 CSS에 갇혀 잘리는 문제는 `createPortal`을 통해 렌더링 위치를 DOM 최상단(body)으로 빼냄으로써 시각적 충돌까지 완벽하게 해결할 수 있다.

## 📝 2차 뼈대 (Dialog.Root) 설계 노트 및 끄적임

Q1. Trigger 버튼에 굳이 ButtonHTMLAttributes를 상속받은 이유는?

결론: 내가 만든 Headless 버튼이 실제 <button> 태그처럼 완벽하게 동작하게 만들기 위함이다. 소비자가 disabled, className, type 등을 자유롭게 넘길 수 있도록 React의 기본 속성을 통째로 상속(...rest)받아 확장성과 재사용성을 극대화했다.

Q2. aria-haspopup="dialog"는 왜 필수인가? (접근성 고려)

결론 (A11y): 눈이 보이지 않는 스크린 리더 사용자에게 "이 버튼을 누르면 대화창이 뜬다"는 것을 사전에 경고하기 위한 웹 접근성 국제 표준(WCAG)이다. 단순한 기능 구현을 넘어 UX 사각지대까지 방어했다.

Q3. Trigger의 onClick에서 내부 open()을 먼저 실행하는 이유는?

결론: 컴포넌트의 '핵심 책임(모달 열기)'을 최우선으로 보장하기 위함이다. 소비자가 외부에서 주입한 onClick 콜백에서 혹시 모를 에러가 발생하더라도, 모달이 열리는 기본 동작 자체는 씹히지 않도록 안전하게 체이닝(Chaining) 처리했다.

Q4. 모달이 닫혀있을 때 DOM 노드를 아예 그리지 않는 이유 (return null)

결론 (성능 최적화): CSS(display: none)로 숨겨두기만 하면 브라우저는 여전히 메모리를 점유하고 렌더링을 계산한다. if (!isOpen) return null;을 통해 DOM 자체를 마운트 해제함으로써 불필요한 메모리 누수를 원천 차단했다. (단, 애니메이션이 필요할 때는 노드를 유지하는 트레이드오프가 발생할 수 있음을 인지하고 있다.)

Q5. createPortal을 써서 모달을 브라우저 최상단(document.body)으로 던진 이유

결론 (스타일 캡슐화): 모달을 일반적인 React 트리 구조에 렌더링하면, 부모 컴포넌트의 overflow: hidden이나 z-index 스태킹 컨텍스트에 갇혀 UI가 깨지거나 숨어버릴 위험이 크다. createPortal을 사용해 상태(Logic)는 React 트리 안에 두되, 물리적인 DOM 위치는 부모의 CSS 영향력을 완벽히 벗어난 document.body로 탈출시켰다.

Q6. Next.js (SSR) 환경을 위한 방어 코드 리팩토링 고찰

결론: 서버 사이드에서는 document 객체가 없기 때문에 렌더링 에러가 발생한다. 커서의 코드는 변수에 할당 후 분기 처리했지만, 나는 가독성과 효율을 높이기 위해 Early Return 패턴을 도입하여 if (typeof document === 'undefined') return null;로 앞단에서 즉시 차단하는 방식으로 개선할 수 있음을 확인했다.

Q7. Overlay(배경)에 aria-hidden="true"를 넣은 이유

결론: 어두운 배경은 순수하게 시각적인 요소일 뿐, 정보를 담고 있지 않다. 스크린 리더가 이 쓸데없는 요소를 읽어 사용자에게 혼란(소음)을 주지 않도록 명시적으로 무시(hidden) 지시를 내렸다.

## 📝 3차 뼈대 (Dialog.Root) 설계 노트 및 끄적임

Q1. useRef<HTMLDivElement>(null)의 작성 방법과 쓰는 이유?

해설: 리액트에서 화면에 그려진 태그(DOM)를 내 손(자바스크립트)으로 직접 멱살 잡고 싶을 때 쓰는 '보이지 않는 갈고리'입니다. 모달 창(div)을 렌더링하고 나서, 그 창에 억지로 포커스를 주기 위해 갈고리를 걸어두는 겁니다.

[MD 변환 결론] "React의 선언적 렌더링 환경에서, 초기 포커스 이동이나 키보드 이벤트 캡처를 위해 실제 DOM 노드에 직접 접근해야 하는 필수적인 예외 상황이 발생한다. 이를 위해 useRef를 사용하여 모달 컨테이너의 참조(Ref)를 안전하게 확보했다."

Q2. querySelectorAll(...)의 저 긴 텍스트는 무슨 역할인가?

해설: 모달 창 안에 있는 수많은 태그 중에서 **"키보드 Tab 키를 눌렀을 때 선택(포커스)될 자격이 있는 놈들"**만 싹 다 긁어모으는 필터링 작업입니다. (버튼, 링크, 인풋창 등)

[MD 변환 결론] "포커스 트랩을 구현하기 위해 모달 내부에 존재하는 '포커스 가능한(Focusable) 모든 요소'를 querySelectorAll로 수집했다. 이 배열의 첫 번째 요소와 마지막 요소를 기준으로 Tab 순환 로직을 구성했다."

Q3. firstElement.focus(); 이게 왜 '앞으로 가기'가 되는가?

해설: 일반적인 상황이 아닙니다. 지금 포커스가 **'맨 마지막 요소'**에 있을 때 Tab 키(앞으로 가기)를 한 번 더 누르면 어떻게 될까요? 원래대로라면 모달 창 밖으로 포커스가 탈출해 버립니다. 그걸 막으려고 "어? 너 마지막에서 탭 눌렀어? 그럼 모달 밖으로 나가지 말고 다시 맨 처음 요소(firstElement)로 돌아가!"라고 억지로 뺑뺑이를 돌리는 겁니다.

[MD 변환 결론] "Focus Trap의 핵심 알고리즘이다. 마지막 요소에서 Tab 키(전진)를 누르면 브라우저 기본 동작(모달 이탈)을 preventDefault()로 막고, 강제로 첫 번째 요소로 포커스를 되돌린다. 반대로 첫 요소에서 Shift+Tab(후진)을 누르면 마지막 요소로 보낸다. 이를 통해 시각 장애인이나 키보드 유저가 모달 밖의 비활성 영역으로 빠지는 치명적인 UX 결함을 방어했다."

## 📝 3, 4차 뼈대 (Content, 접근성 속성) 설계 노트

Q1. 모달이 열릴 때 포커스를 강제로 납치(focus())해야 하는 이유는?

결론 (웹 접근성 - A11y): 마우스를 쓰지 못하는 키보드 유저나 스크린 리더 유저를 위한 필수 조치다. 모달이 열렸는데 포커스가 여전히 모달 뒤의 원래 페이지에 남아있으면, 유저는 허공에서 길을 잃게 된다.

Q2. useRef를 사용하여 DOM에 직접 접근한 이유는?

결론: React의 선언적 패러다임 내에서, 초기 포커스 강제 이동과 키보드 트랩 배열 수집(querySelectorAll) 등 브라우저 기본 동작을 세밀하게 제어하기 위해 useRef로 DOM 참조를 확보했다.

Q3. Focus Trap (포커스 트랩) 알고리즘 설계

결론: 모달 내부의 Focusable 요소를 긁어모아 배열로 만든 뒤, 마지막 요소에서 Tab(전진) 시 첫 요소로, 첫 요소에서 Shift+Tab(후진) 시 마지막 요소로 강제 순환(focus())시켰다. 이로써 포커스가 모달 밖으로 탈출하여 비활성 영역을 탐색하는 치명적인 UX 결함을 완벽히 방어했다.

Q4. 4차 뼈대 (Title, Description)의 aria-labelledby 연결 로직

결론: Root에서 useId()로 생성한 고유 ID를 Context로 내려받아, Content 창과 Title/Description 텍스트를 논리적으로 묶어주었다. 개발자가 일일이 ID를 하드코딩하지 않아도 스크린 리더가 "이 모달의 제목은 OO입니다"라고 정확히 읽어낼 수 있게 캡슐화했다.
