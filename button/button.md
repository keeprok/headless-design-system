# 🧩 Headless Button Component 설계 노트

## 1. 컴포넌트의 목적

UI(스타일)와 비즈니스 로직을 강제하지 않고, 버튼이 가져야 할 **'웹 접근성(A11y)'**과 **'다형성(Polymorphism)'**을 완벽하게 보장하는 Headless 코어 컴포넌트입니다. 어떠한 디자인 시스템에서도 안전하게 확장하여 사용할 수 있도록 설계되었습니다.

---

## 2. 핵심 아키텍처 및 트러블슈팅

### A. 다형성(Polymorphism)과 타입 안전성

- **문제:** 버튼이 시맨틱 웹을 준수하기 위해 때로는 `<a>` 태그로, 때로는 Next.js의 `<Link>` 태그로 렌더링되어야 하는 요구사항이 발생합니다.
- **해결:** `as` prop과 `extends React.ElementType` 제네릭을 도입하여 렌더링될 태그를 동적으로 교체할 수 있게 설계했습니다.
- **트러블슈팅 (`forwardRef` 제네릭 소실):** 다형성을 부여한 컴포넌트를 `forwardRef`로 감싸면 제네릭 타입 파라미터가 소실되는 TypeScript의 고질적인 한계가 있었습니다. 이를 해결하기 위해 순수 렌더 함수(`ButtonRender`)를 분리하고, export 시점에 `as`를 통한 타입 단언(Type Assertion)으로 외부 시그니처를 복원하는 패턴을 적용했습니다.

### B. Slot 패턴 (`asChild`) 도입

- **설계 의도:** 부모가 정의한 Button의 접근성 로직과 이벤트 통제권을, 렌더링될 자식 컴포넌트에게 그대로 위임(Delegation)하기 위해 Radix UI의 `Slot` 패턴을 차용했습니다.
- **구현:** `asChild`가 true일 경우 `React.cloneElement`를 통해 자식 요소에 병합된 onClick 이벤트와 aria 속성들을 안전하게 주입합니다.

### C. 완벽한 웹 접근성 (WAI-ARIA) 제어

- **`disabled` vs `aria-disabled` 분리:** 네이티브 `disabled` 속성은 키보드 포커스조차 불가능하게 만들어 스크린 리더 사용자가 요소의 존재를 인지할 수 없게 만듭니다. 이를 해결하기 위해 네이티브 `<button>` 태그에만 `disabled`를 부여하고, 다형성으로 렌더링된 다른 태그나 로딩(`isLoading`) 상태일 때는 `aria-disabled="true"`와 이벤트 캡처링 차단(`e.preventDefault`)을 통해 논리적 차단과 접근성 인지를 동시에 달성했습니다.

## 3. 면접 방어용 Q&A (자가 검증)

**Q1. 네이티브 button 태그에 `disabled` 속성을 주면 되는데, 왜 굳이 `aria-disabled`를 분리해서 처리했나요?**
A. 접근성(UX) 때문입니다. 네이티브 `disabled`는 포커스 자체를 막아버려 스크린 리더 사용자가 해당 위치에 버튼이 있다는 사실조차 인지할 수 없습니다. 반면 `aria-disabled`는 포커스는 허용하되 "현재 비활성화 상태임"을 읽어주어, 사용자가 상태가 변경되기를 기다릴 수 있도록 배려하는 국제 접근성 표준(A11y)입니다.

**Q2. `Omit`을 사용해 기본 HTML 속성을 제거한 이유가 무엇인가요?**
A. 타입 충돌을 방지하기 위해서입니다. HTML이 기본적으로 가진 속성과 제가 커스텀으로 정의한 Props(`asChild` 등) 간에 타입스크립트 추론 충돌이 발생할 수 있습니다. `Omit`을 통해 기본 속성에서 겹칠 수 있는 키를 미리 제거하여, 라이브러리를 가져다 쓰는 동료 개발자에게 정확하고 안전한 자동완성(DX)을 제공하기 위함입니다.
