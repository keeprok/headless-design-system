## Dialog

### Context vs Props

**문제:** Compound Component는 사용자가 마크업을 자유롭게 조립한다. 그래서 라이브러리 제작자는 자식이 몇 단계 깊이에 위치할지 **미리 알 수 없다.** props로 `titleId`·`close`를 내리려면 중간 컴포넌트를 전부 거쳐야 하는데, 구조를 모르니 경로를 고정할 수 없고, 전달 단계가 길수록 누락·추적 비용이 커진다.

**선택:** 상태·함수를 Context에 담고, 자식이 Ex:`useDialogContext()`로 **직접 구독**한다. 중간 컴포넌트는 값을 몰라도 되고, 조립 구조와 무관하게 필요한 자식이 바로 꺼낸다.

**트레이드오프:** context의 `value`가 바뀌면, 그 Context를 `useContext`로 **구독하는 모든 컴포넌트가 리렌더링된다.** 일부만 쓰는 값이 바뀌어도 구독자 전체가 다시 그려질 수 있어, 큰 앱에서는 불필요한 리렌더링(over-rendering)이 성능 문제가 된다. 그래서 모든 상태를 Context에 넣지는 않는다.

### aria-labelledby vs aria-label

**문제:** 모달의 접근성 이름을 `aria-label="회원 정보 수정"`처럼 직접 문자열로 박으면, 화면의 `<h2>` 제목과 **같은 텍스트가 두 곳에 중복**된다. 제목이 바뀌면 두 곳을 다 고쳐야 하고, 하나라도 놓치면 화면과 스크린리더가 다른 이름을 말하는 불일치가 생긴다.

**선택:** `aria-labelledby`로 화면의 `<h2>` id를 참조한다. 제목은 h2 한 곳에만 존재하고, 스크린리더는 그걸 따라 읽으므로 **단일 출처(DRY)**가 유지되어 자동 동기화된다.

**트레이드오프(첫 추측):** "labelledby는 일관성이 너무 강해서 유연하게 쓰기 어려운 게 단점 아닐까?"

**트레이드오프:** `aria-labelledby`는 **참조할 실제 요소(화면에 보이는 제목)가 존재해야만** 쓸 수 있다. 만약 디자인상 **시각적 제목이 없는 모달**(예: 아이콘만 있는 모달)이라면, 가리킬 h2가 없으므로 이 방식을 쓸 수 없고 그때는 `aria-label`로 직접 이름을 줘야 한다.
