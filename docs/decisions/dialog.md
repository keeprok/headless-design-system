# Headless Design System — Decision Log

## "AI 도구로 빠르게 구현하되, 모든 설계 결정을 스스로 검증하고 문서화했습니다. 각 항목은 '왜 이 선택을 했는가'와 '무엇을 포기했는가(트레이드오프)'를 담습니다.

## Dialog

### Context vs Props

**문제:** Compound Component는 사용자가 마크업을 자유롭게 조립한다. 그래서 라이브러리 제작자는 자식이 몇 단계 깊이에 위치할지 **미리 알 수 없다.** props로 `titleId`·`close`를 내리려면 중간 컴포넌트를 전부 거쳐야 하는데, 구조를 모르니 경로를 고정할 수 없고, 전달 단계가 길수록 누락·추적 비용이 커진다.

**선택:** 상태·함수를 Context에 담고, 자식이 Ex:`useDialogContext()`로 **직접 구독**한다. 중간 컴포넌트는 값을 몰라도 되고, 조립 구조와 무관하게 필요한 자식이 바로 꺼낸다.

**트레이드오프:** context의 `value`가 바뀌면, 그 Context를 `useContext`로 **구독하는 모든 컴포넌트가 리렌더링된다.** 일부만 쓰는 값이 바뀌어도 구독자 전체가 다시 그려질 수 있어, 큰 앱에서는 불필요한 리렌더링(over-rendering)이 성능 문제가 된다. 그래서 모든 상태를 Context에 넣지는 않는다.

### aria-labelledby vs aria-label

**문제:** 모달의 접근성 이름을 `aria-label="회원 정보 수정"`처럼 직접 문자열로 박으면, 화면의 `<h2>` 제목과 **같은 텍스트가 두 곳에 중복**된다. 제목이 바뀌면 두 곳을 다 고쳐야 하고, 하나라도 놓치면 화면과 스크린리더가 다른 이름을 말하는 불일치가 생긴다.

**선택:** `aria-labelledby`로 화면의 `<h2>` id를 참조한다. 제목은 h2 한 곳에만 존재하고, 스크린리더는 그걸 따라 읽으므로 **단일 출처(DRY)**가 유지되어 자동 동기화된다.

**트레이드오프(첫 추측):** "labelledby는 일관성이 너무 강해서 유연하게 쓰기 어려운 게 단점 아닐까?"

실제 트레이드오프: aria-labelledby는 화면에 렌더링 된 참조할 실제 요소(화면에 보이는 제목)가 존재해야만 쓸 수 있다. 만약 디자인상 시각적 제목이 없는 모달(예: 아이콘만 있는 모달)이라면, 가리킬 h2가 없으므로 이 방식을 쓸 수 없고 그때는 aria-label로 직접 이름을 줘야 한다. 즉, 헤드리스 컴포넌트가 이를 강제하면 사용자의 UI 설계 자율성이 침해된다.

개선 방안: 시각적 제목 유무를 사용자가 선택할 수 있도록 분기 처리. aria-label prop을 직접 넘기면 시각적 제목 없이 독립적으로 작동하고, 넘기지 않으면 Context가 titleId를 생성해 aria-labelledby로 자동 연결되도록 구조 개선. (A11y와 헤드리스 철학 동시 충족)

### useEffect로 모달 열릴 때 focus를 모달 안으로 강제로 옮긴다. 이걸 안 했다면 생겼을 문제는?

문제: (포커스를 옮기지 않으면) 마우스·시각 사용자는 문제없지만, 키보드·스크린리더 사용자는 조작하는 것(키보드 위치)과 듣는 것(스크린리더 음성)이 불일치한다.

선택: 모달이 열리는 순간 focus를 모달 컨테이너로 옮겨서, 키보드·스크린리더 사용자가 즉시 모달을 조작할 수 있게 한다.

트레이드오프: 현재 코드는 모달 열 때 focus를 안으로 가져오지만, 닫을 때 focus를 원래 위치(모달을 연 트리거 버튼)로 되돌리는 로직이 없다. 그래서 모달을 닫으면 focus가 body로 떨어져 키보드 사용자가 이전 위치를 잃는다.

개선 방안: 모달 열기 전 document.activeElement를 저장해두고, 닫힐 때 그 요소로 focus()를 되돌리면 된다(focus restoration).

### Tab 트랩 코드에서 e.preventDefault()가 왜 필요한가?

문제: preventDefault가 없으면 마지막 요소에서 Tab을 눌렀을 때 브라우저 기본 동작이 focus를 모달 밖으로 혹은 문서 위로 보낸다. 그래서 포커스 트랩이 유지 안 된다.

선택: 브라우저 기본 동작을 덮어쓰고 커스텀 focus 로직을 강제하려고 preventDefault로 네이티브 Tab 동작을 막는다.

트레이드오프: preventDefault로 브라우저 기본 동작을 막는 순간, focus 이동을 전부 우리가 수동으로 책임져야 한다. focus() 호출 로직에 버그가 있으면 focus가 아예 갇히거나 사라질 수 있다. 즉, 제어권을 가져온 대가로 구현 책임도 커진다.

### Esc의 stopPropagation — preventDefault와 뭐가 다른지(동작 vs 전파), 중첩 모달에서 왜 필요한지

**문제:** Esc 키 이벤트가 발생하면, 브라우저와 React의 이벤트 시스템은 이 이벤트를 부모 요소로 계속 **버블링**시킨다. 만약 이 Dialog가 다른 Dialog 안에 중첩되어 있고 바깥에도 ESC keydown 리스너가 있다면, ESC 한 번에 **양쪽 리스너가 모두 발화**해서 두 모달이 동시에 닫히는 참사가 생긴다.

**선택:** ESC 처리 안에 `e.stopPropagation()`을 넣어, 이벤트가 부모 트리로 올라가는 것을 막는다. 그러면 이벤트가 **가장 안쪽 모달에서 소비**되고, 사용자 기대대로 "가장 위 모달 하나만" 닫힌다.

**핵심 (오해 주의):** `preventDefault`는 **동작**을 막고(전파는 계속), `stopPropagation`은 **전파**를 막는다(동작은 계속). 축이 다르므로 대체재가 아니다.

**트레이드오프:** `stopPropagation`은 "가장 안쪽 하나만 닫힘"을 보장하지만, 그 대가로 **바깥 모달까지 함께 닫고 싶은 시나리오는 불가능**해진다. 예를 들어 "최종 확인 모달 → 원본 모달"을 ESC 한 번으로 함께 닫는 UX는 이 코드에선 안 된다.

**개선 방향:** 격리 여부를 사용자가 결정하도록, `DialogRoot`에 `closeOnEscape` 또는 `escapePropagates` 같은 prop을 추가해 기본은 격리(현재 동작), 옵션으로 전파 허용을 열어줄 수 있다. 헤드리스 철학(제어권 위임)과 일치한다.

### createPortal — 왜 모달을 부모 내부가 아닌 body에 붙이는가

**문제:** 모달을 부모 컴포넌트 내부에 그대로 렌더링하면, DOM 트리상 조상 중 하나라도 `overflow: hidden`·`z-index`·`transform` 같은 속성을 가진 순간 **stacking context에 갇혀** 화면 위로 못 뜬다. 사용하는 개발자가 이걸 매번 신경 써야 하는 유지보수 부담이 생긴다.

**선택:** `createPortal(children, document.body)`로 모달을 `body`에 직접 붙인다. React 트리상의 부모-자식 관계(Context, 이벤트 버블링)는 그대로 유지되면서, DOM 트리상으로는 조상의 stacking context 바깥에 위치한다. 어떤 부모 스타일에도 영향받지 않고 항상 최상단에 뜰 수 있다.

**트레이드오프:** Portal로 렌더링된 요소는 DOM 트리상 `body`의 자식이므로, 부모 컴포넌트의 CSS 변수나 테마 클래스가 DOM 상속으로 전달되지 않을 수 있다. 테마를 CSS 변수로 관리할 경우, Portal 대상(`document.body`)에도 해당 변수가 정의되어 있어야 스타일이 깨지지 않는다.

### role="dialog" + aria-modal — 스크린리더 격리와 focus trap의 짝

**문제:** 시각적 오버레이(어두운 배경)는 눈에만 보인다. 스크린리더는 그 어둠을 못 본다. 그래서 `aria-modal`이 없으면 스크린리더 커서는 배경 콘텐츠를 계속 읽고 돌아다닌다. 반면 키보드 focus는 focus trap 덕분에 모달 안에 갇혀 있다. **두 채널이 서로 다른 곳을 가리키는 desync가 발생**한다. 키보드+스크린리더를 함께 쓰는 시각장애 사용자는 "내 손은 여기 있는데 왜 다른 게 읽히지?" 하고 길을 잃는다.

**선택:** `aria-modal="true"`를 붙여 스크린리더에게 **"이 모달이 열려있는 동안 바깥은 없는 셈 쳐라(inert)"**고 지시한다. 그러면 스크린리더 탐색 범위가 모달 안으로 격리되고, focus trap과 **같은 곳**을 가리키게 된다.

**핵심 (focus trap과의 짝):**
Focus Trap (`handleKeyDown`) = **키보드** 사용자를 모달에 격리 / `aria-modal="true"` = **스크린리더** 사용자를 모달에 격리. 다른 사용자층, 같은 목적(격리). 둘이 짝을 이뤄야 모달이 진짜로 작동한다.

**트레이드오프:** `aria-modal="true"`는 스크린리더에게 "바깥을 무시하라"고 **선언**할 뿐, 실제로 배경 요소의 접근성을 강제로 끄지는 않는다. 구형 스크린리더나 일부 브라우저 조합에서 완벽히 지원되지 않을 수 있다.

**개선 방향:** 더 견고하게 하려면, 모달이 열릴 때 **배경 요소들에 직접 `inert` 속성이나 `aria-hidden="true"`를 걸어** 이중 안전장치를 둘 수 있다. 이러면 스크린리더가 선언을 무시하더라도 물리적으로 배경 접근이 차단된다.

### Tab Focus Trap — 없다면 무슨 문제가 생기는가

**문제:** 처음 모달에 진입했을 때는 focus 이동만으로 충분하지만, 마지막 요소에서 Tab을 눌러 다시 첫 요소로 돌아오려 할 때 Tab Focus Trap이 없다면 focus가 모달 밖으로 탈출한다. 사용자가 의도한 순환이 불가능해진다.

**선택:** `handleKeyDown`에서 focusable elements 목록을 구하고, **마지막 요소에서 Tab → 첫 요소로**, **첫 요소에서 Shift+Tab → 마지막 요소로** 강제 순환시킨다. 이때 `e.preventDefault()`로 브라우저의 기본 Tab 이동을 막고, `.focus()`로 원하는 대상에 직접 옮긴다. focus를 **순환 고리로 가둔다.**

**트레이드오프:** focus 순환을 직접 구현하는 대가로 **구현의 정확성 부담**이 온다. `querySelectorAll`로 focusable elements를 매번 계산하는데, DOM이 동적으로 변하면 캐시 없이 매번 새로 스캔해야 하고 놓치면 순환이 깨진다. focusable 판정 셀렉터(`button, [href], input, ...`)가 불완전할 수 있고(`contenteditable`, `audio[controls]` 등은 안 잡힌다), focusable 요소가 0개면 로직이 무의미하고 1개면 순환이 자기 자신으로 돌아 시각적으로 아무 일도 안 일어난다.

**개선 방향:** 이런 세부를 직접 관리하는 대신 `focus-trap-react` 같은 검증된 라이브러리를 쓰거나, 향후 브라우저 표준으로 오는 `<dialog>` 요소의 네이티브 focus 관리에 위임하는 방향도 고려할 수 있다.
